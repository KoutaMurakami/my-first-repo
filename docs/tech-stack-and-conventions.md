# 技術選定・開発方針

アプリ開発の「裏側」の意思決定を記録するドキュメント。いわゆるADR(Architecture Decision Record)的な位置づけで、後から「なぜこの技術・この書き方にしたのか」を振り返れるようにするためのもの。

- 作成日: 2026年8月

## 1. 採用技術スタック

| 層 | 技術 | 役割 |
|----|------|------|
| アプリ本体 | Flutter (Dart) | iOS/Android両対応のスマホアプリ本体を作るフレームワーク |
| ローカルDB | Drift (SQLiteベース) | オフライン対応のため端末内に保存するデータベース |
| クラウド/バックエンド | Supabase (PostgreSQLベース) | 認証・クラウド同期・データ保存を担うバックエンド |

## 2. なぜこの組み合わせにしたか

- **こだわりより汎用性を優先**：開発者(自分)は特定技術への強いこだわりは無く、「使い勝手が良く、メジャーで、実務でも通用する」ことを最優先条件とした
- **学習効果も重視**：本アプリの開発完了後、使用した技術やコードの意味・意図を振り返って学習に活かしたいという狙いがある。そのため、ニッチな技術より汎用性の高い技術を選定した
- **SQLで統一できる**：ローカルDB(Drift/SQLite)とクラウドDB(Supabase/PostgreSQL)の両方が「本物のSQL」をベースにしている。NoSQL系サービス(Firebase等)も選択肢にはあったが、SQLは業界を問わずどこでも通用する汎用スキルであり、今回の学習目的と最も合致すると判断した
- **Flutterは求人・実務でも見かける定番のクロスプラットフォームフレームワークであり、1つのコードでiOS/Androidに対応できる点も採用理由**

## 3. コーディング方針(学習教材としての活用)

このリポジトリは単なる成果物ではなく、開発者自身の学習教材としても機能させることを目的とする。そのため、コードを書く際は以下を徹底する。

- **なぜこの技術・この書き方を選んだか**をコメントや関連ドキュメントとして残す
- **このコードが何をしているか(意味・意図・役割)**を分かりやすく説明として残す
- 後から読み返した時に、「動くだけのコード」ではなく「理解できるコード」になっていることを目指す

## 4. ドキュメント運用ルール

- 要件定義・技術選定などの背景ドキュメントは `docs/` 配下にmdファイルとして `main` ブランチに直接記録する
- 機能実装は `main` から切った `feature/xxx` ブランチで進め、開発の過程をGitHub履歴として残す
